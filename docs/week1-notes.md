# v0.1 1주차 메모: 알려진 한계

1주차 관측 배관(execve → ring buffer → 로더 → JSON)의 알려진 한계.
"시점"은 해결 예정 시점이다. 해결하면 체크하고, "해결" 줄에 해결 커밋의 제목을 적는다.

## 해결할 것

### 로그 무결성

- [x] **loader.c가 filename을 JSON 이스케이프하지 않음**
  - 이유: 따옴표·개행이 든 파일 이름을 exec하면 가짜 JSON 줄을 끼워 넣어 로그를 위조할 수 있다.
  - 시점: w1d3
  - 해결: "w1d3: 탐지기 디스패처와 더미 탐지기, JSON 이스케이프 추가"
- [ ] **드롭 수가 로더 종료 때 한 번, 전체 합계로만 출력됨** (`loader.c`, `run_scenarios.sh`)
  - 이유: 실행 중에는 드롭을 볼 수 없고, 어느 세션(시나리오)의 이벤트가 버려졌는지 나뉘지 않는다. 로더가 SIGKILL 이나 크래시로 끝나면 출력되지 않고, 맵을 pin 하지 않아 나중에 읽을 수도 없다. 러너는 드롭이 있으면 실행 전체를 실패로 보지만 어느 시나리오인지는 알려 주지 못한다.
  - 시점: w5
  - 해결: (미해결)

  - 이유: sys_enter_execve만 붙어 있어 execveat(fexecve 포함)으로 실행하면 이벤트가 남지 않는다.

- [ ] **세션마다 부트스트랩 EXEC(/proc/self/exe)가 먼저 기록됨**
  - 이유: mycontainer_run이 phase2 진입을 위해 스스로를 re-exec하는 것이므로, 탐지기가 이를 에이전트 행동으로 오인하지 않게 걸러야 한다.
  - 비고: w2d3 결정으로 v0.2 이후로 미룬다. write_exec_boundary 는 TAG_HIT 만 보므로 영향이 작고, 더미 탐지기만 이 EXEC 를 SUSPECT 로 판정한다.
  - 시점: v0.2 이후 (w2d3 결정으로 미룸)
  - 해결: (미해결)
- [ ] **sh -c 의 마지막 명령으로 실행한 /tmp/trigger 의 execve 이벤트가 컨테이너 안에서 관측되지 않음**
  - 이유: '; true' 를 붙이면 관측됨 (s99 시나리오로 재현). 4일차부터 s99 명령에 '; true' 가 붙어 있어서 이 현상이 가려져 있었다.
  - 비고: 호스트 busybox strace 로는 두 경우 모두 execve 가 호출되어 BPF 프로그램 또는 로더 쪽을 의심한다. 원인 미상. s00 의 실제 로그(tools/fixtures/real_s00_benign)에서는 /bin/ls 가 /bin/sh 와 같은 pid 로 제자리 실행되었는데도 정상 관측되었으므로 제자리 exec 자체가 원인은 아니며, 실행 대상이 직접 만든 #!/bin/sh 스크립트라는 점이 차이일 수 있다 (미확인). 2주차 월요일에 로더를 직접 띄워 두 스크립트를 비교하면서 조사한다. w2d1 조사: 로더를 직접 띄운 수동 실행(4회)과 러너 경유 실행(34회)에서 '; true' 없는 제자리 exec 가 모두 관측되어 재현되지 않았다. #!/bin/sh 스크립트라는 점도 차이가 아니었다. 38회 중 누락 0회이며 원인은 규명하지 못했다. 로더는 10/3 빌드, run_container.sh 는 10/4 수정본 기준(VM 시각)이고 FAIL 당시와 같은 빌드였는지는 확인하지 못했다.
  - 시점: w2
  - 해결: (미해결. w2d1 재현 불가, 원인 미규명)

### fail-closed

- [x] **로더가 꺼져도 pin된 map이 남아 있어 agent-run이 조용히 성공함**
  - 이유: map 등록은 성공하지만 프로그램이 detach돼 있어 관측 없이 세션이 실행된다.
  - 시점: w3 (3주차 초, 실제 kill 구현 전)
  - 해결: "w3d1: 로더 생존을 flock 잠금으로 확인하고 없으면 세션을 시작하지 않음"
- [x] **bpf_obj_get 실패 시 아무 출력 없이 진행함** (`mycontainer_run.c`)
  - 이유: 로더를 한 번도 띄우지 않아 map이 없을 때도 감시 없이 컨테이너가 실행되고, 사용자는 이를 알 수 없다.
  - 시점: w3 (3주차 초, 실제 kill 구현 전)
  - 해결: "w3d1: 감시 맵을 못 열거나 등록하지 못하면 세션을 시작하지 않음"
- [x] **ring buffer 드롭 카운터 없음**
  - 이유: 버퍼가 가득 차면 `bpf_ringbuf_reserve` 실패로 이벤트가 버려지는데, 몇 개가 버려졌는지 남지 않아 로그 누락을 감지할 수 없다.
  - 시점: w3 (3주차 초, 실제 kill 구현 전)
  - 해결: "w3d2: 러너가 로더의 ring buffer 드롭 수를 읽어 0 이 아니면 인프라 검증 실패"
- [ ] **탐지기가 연속 오류 5회를 내면 영구히 꺼지고, 알림은 stderr 한 줄뿐** (`dispatcher.c`)
  - 이유: 꺼진 탐지기를 다시 켜는 경로가 없어, 이후 세션 내내 그 탐지기의 판정이 나오지 않는다.
  - 비고: 공격자가 오류를 유발해 탐지기를 끌 수 있음(fail-open), kill switch 연결 시 fail-closed 정책과 함께 결정
  - 시점: w3
  - 해결: (미해결)
- [x] **탐지기가 16개(MAX_DETECTORS)를 넘으면 경고만 남기고 등록하지 않음** (`dispatcher.c`)
  - 이유: 등록에 실패한 탐지기가 빠진 채로 로더가 정상 시작해, 감시가 빠졌다는 사실을 알기 어렵다.
  - 비고: 등록은 main 이전이라 실패 플래그를 세우고 main에서 시작을 거부하는 방식 검토. w2d3 결정으로 v0.2 이후로 미룬다. 지금 탐지기는 몇 개뿐이라 급하지 않고 탐지기가 늘 때 다시 본다.
  - 시점: v0.2 이후 (w2d3 결정으로 미룸)
  - 해결: "w3d2: 탐지기 개수가 상한을 넘으면 등록을 거부하고 시작하지 않음"
- [x] **등록된 탐지기 목록을 시작 시 출력하지 않고, 같은 이름도 중복 등록됨** (`dispatcher.c`)
  - 이유: 어떤 탐지기가 켜졌는지 확인할 수 없고, 같은 탐지기가 두 번 판정을 낼 수 있다.
  - 비고: w1d3 의 탐지기 중복 판정 사건이 계기.
  - 시점: w3 (3주차 초, 실제 kill 구현 전)
  - 해결: "w3d2: 탐지기 이름이 비었거나 중복이면 등록을 거부하고 시작 시 목록을 출력"

### 세션 대응과 kill switch

- [x] **kill 구현에 세션의 cgroup 경로가 필요한데 지금은 id만 있음**
  - 이유: cgroup 경로가 있어야 cgroup.kill 등으로 세션을 종료할 수 있다.
  - 비고: 새 필드 없이 세션 ID 끝 숫자로 `/sys/fs/cgroup/mycontainer-<숫자>` 를 만들고, 디렉토리를 fd 로 열어 inode 가 cgroup_id 와 같을 때만 `cgroup.kill` 에 쓴다 (`kill_cgroup.c`).
  - 시점: w3
  - 해결: "w3d2: BLOCK 이면 세션 cgroup 을 cgroup.kill 로 종료하고 결과를 기록 (sent/already_gone/failed/skipped)"
- [x] **BLOCK이면 무조건 종료할지, 평가용 관찰 모드를 둘지 정하지 않음**
  - 이유: 오탐 평가 중에는 종료 없이 BLOCK 판정만 모아야 할 때가 있다.
  - 비고: 평가용으로만 쓰고 README 에 명시. 기본값이 되면 이 도구의 의미가 사라짐.
  - 시점: w3
  - 해결: "w3d2: 로더 관찰 모드(--no-kill) 추가, BLOCK 시 종료 대신 would_kill 기록"
  - 확인: 기본은 종료, --no-kill 이면 would_kill 만 기록. 단위 테스트(test_kill_session, test_verdict_handler)와 mock, VM 에서 실제 로더와 컨테이너로 수동 확인 (rc=0, would_kill 세션당 한 줄)

  - 이유: 러너가 로더를 끌 때 TERM 을 보낸 뒤 wait 로 끝나기를 무한정 기다린다 (run_scenarios.sh 의 stop_loader 함수, 그 안의 wait). "w3d2: 러너가 ready 시간 초과 뒤에도 로더를 끄도록 고치고 회귀 테스트 추가" 커밋의 수정으로 ready 시간 초과 분기도 이 wait 를 지나게 되어, 로더가 커널 안에서 멈춰 TERM 에 반응하지 않으면 러너의 EXIT 정리가 끝나지 않는다. 진짜 로더는 TERM 을 받으면 stop 플래그만 세우므로 BPF 로드 도중이면 로드가 끝난 뒤에야 끝난다.
  - 비고: 완화책은 TERM 을 보내고 몇 초 기다린 뒤 살아 있으면 KILL 을 보내는 것이다. 다만 커널 안에서 멈춘(D state) 프로세스는 KILL 에도 반응하지 않을 수 있다. 정상 종료 때의 stop_loader 호출도 같은 함수를 쓴다.
  - 시점: w5

## 수용한 한계

고치지 않고 감안해서 설계할 성질. 체크박스를 쓰지 않는다.

- **busybox 내장 명령은 execve가 보이지 않을 수 있음**
  - 이유: 셸 내장(applet)으로 처리되면 새 프로그램을 exec하지 않으므로 커널에서 관측할 지점이 없다.
  - 반영: README 한계 섹션(w5), 시나리오 작성 규칙(w2부터: 명령은 경로를 명시하고 이벤트가 실제로 나오는지 먼저 확인), v0.2 실제 에이전트 rootfs와 이벤트 양 비교
- **pid만으로 프로세스를 구분하면 안 됨**
  - 이유: exec는 PID를 유지하므로 같은 pid에서 서로 다른 프로그램의 이벤트가 연달아 나온다.
  - 반영: w2 설계 메모(태깅 키), README 한계 섹션
- **탐지기가 세그폴트를 내면 로더 프로세스 전체가 죽음** (`dispatcher.c`)
  - 이유: 탐지기 계층의 fail-open. C에는 예외 처리가 없어 오류 격리는 반환값으로만 가능하고, 완전한 격리에는 탐지기를 별도 프로세스로 분리해야 한다.
  - 반영: README 한계 섹션(w5), 프로세스 분리는 v0.3 이후 검토
- **탐지기 실행 순서가 보장되지 않음**
  - 이유: 탐지기는 constructor로 등록되는데, 파일 간 constructor 호출 순서는 C 표준이 정하지 않으며 링크 순서(build.sh의 detectors/*.c 확장 순서)와 툴체인에 따라 달라진다.
  - 반영: w2 설계 메모(탐지기는 서로 독립이고 실행 순서에 의존하지 않는다는 작성 규칙)
- **json_escape가 0x80 이상 바이트를 그대로 출력함** (`json_escape.c`)
  - 이유: 유효하지 않은 UTF-8 바이트열이 섞이면 일부 JSON 파서가 그 줄을 거부할 수 있다.
  - 반영: w5 로그 스키마 확정 시 파서 동작 확인, README 한계 섹션
- **로그 쓰기가 동기식이라 디스크가 막히면 수신 루프도 멈춤** (`session_log.c`)
  - 이유: 쓰기마다 fflush 하는 동기식이라 디스크 지연이 ring buffer 수신을 멈춘다.
    측정(부하 시험 전, 14회 기록): log stats: writes=14, slow(>5ms)=0, max=104us, lost=0.
    exec가 몰리는 정상 워크플로우(w3 목요일)에서 다시 측정한다.
  - 반영: 종료 시 log stats 로 확인, 나쁘면 스레드 분리
- **세션 칸 64개를 넘으면 밀려난 세션의 kill_requested가 사라짐** (`session_log.c`)
  - 이유: 밀려났다 다시 열린 세션에서 BLOCK이 오면 종료 요청이 한 번 더 나간다. 그 cgroup 이 이미 없으면 already_gone, 아직 있으면 sent 가 다시 나갈 수 있다.
  - 비고: 관찰 모드(--no-kill)에서는 cgroup 이 살아 있어서, 밀려났다가 다시 열린 세션에서 would_kill 이 한 줄 더 남을 수 있다 (코드에서 읽은 추론이며 테스트로 확인하지 않았다).
  - 반영: README 한계 섹션
- **세션이 끝나도 by-cgroup 링크가 남음** (`run_container.sh`)
  - 이유: 정리하는 코드가 없어 끝난 세션의 링크가 sessions/by-cgroup 에 쌓인다.
  - 반영: 세션 폴더 정리 시 같이 삭제
- **에이전트는 사용자 네임스페이스 안 root(uid 0, 전체 capability)로 실행됨. 하드닝은 미적용**
  - 이유: VM 확인 결과 id=0, CapEff=000001ffffffffff, 호스트 기준 uid 1000 (w2d1). 비root, capability 축소, no_new_privs는 일반 권장 사항이지만 v0.1에서는 실험에서 바뀌는 조건을 늘리지 않으려고 적용하지 않았다. 컨테이너 안 /tmp 는 root 소유 drwxrwxr-x 라서 비root 전환에는 rootfs 권한 정리와 uid_map 확장이 필요하다.
  - 반영: 위협 모델 신뢰 가정에 명시. 탐지기가 선 뒤 별도 작업으로 cap 축소와 no_new_privs, 이어서 비root 전환을 시도하고 s00/s99 이벤트가 같은지 비교 (w3 이후, 선택)
- **세션 kill은 세션 밖에서 일어난 실행을 멈추지 못함**
  - 이유: kill_session 은 세션 cgroup 안의 프로세스만 끊는다. 쓰기→실행 탐지기의 BLOCK 도 판정이 exec 이후에 나오므로 의미는 후속 행동 중단이다.
  - 반영: 위협 모델 "차단의 두 가지 의미"와 README 한계 섹션(w5)에 "차단 = 사후 종료" 명시. 커널 안 거부는 v0.3 실험 후보
- **쓰기 태깅은 open 시점의 쓰기 모드만 대상으로 하며 rename, hardlink, mmap 쓰기, 복사 후 실행은 탐지하지 못함**
  - 이유: 계획서 월요일 설계대로 security_file_open 에서 쓰기 모드 open 시점에 태깅한다. 다른 경로로 만들어진 파일은 맵에 태그가 없어 미탐이 된다.
  - 반영: 설계 메모에 미탐 범위로 기록, 오탐/미탐 평가 시 제한된 재현 시나리오에 기반함을 README에 명시 (w5)
- **TLS 내용은 볼 수 없음**
  - 이유: 커널에서 보이는 것은 암호화된 바이트라 평문 내용을 알 수 없다. 평문 관측에는 사용자 공간 라이브러리 uprobe 나 프록시가 필요하며 v0.1 범위 밖이다. 영향은 v0.2 송신 탐지기에서 목적지는 보되 전송 내용은 못 보는 형태로 나타난다.
  - 반영: README 한계 섹션(w5), v0.2 송신 탐지기 설계 때 다시 검토
- **에이전트가 쓴 파일이 exec 대상이 아니라 인터프리터의 인자나 설정으로 읽히는 실행은 탐지하지 못함**
  - 이유: security_bprm_check 가 exec 되는 파일의 신원만 write_tags 에서 조회한다. 같은 파일을 호스트에서 `sudo sh <파일>` 로 실행하면 TAG_HIT 이 생기지 않고 직접 실행하면 BLOCK 이 난다 (w2d3, sh 한 번 기준 VM 확인). python, node 같은 다른 인터프리터와 설정 파일 안의 명령은 같은 원리로 추정하며 직접 확인하지 않았다. 읽기 open 은 조회하지 않는다.
  - 반영: 위협 모델 4.3절 미탐 행에 추가, README 한계 섹션(w5). 읽기 open 조회(EVT_OPEN)는 오탐 측정 뒤 v0.2 이후에 검토
- **러너가 run_container.sh 의 출력 형식과 이름 규칙에 의존함** (`run_scenarios.sh`)
  - 이유: 러너는 agent-run 출력의 "[*] 세션 시작: <ID> (cgroup_id=...)" 줄에서 세션 ID 를 뽑고, host.sh 스텝은 컨테이너 폴더가 "mycontainer-<세션 ID 의 끝 숫자>" 라는 이름 규칙으로 upperdir 를 찾는다. 이 두 가정은 여러 세션에서 관찰로 확인했을 뿐 run_container.sh 코드로 확인하지 않았다. 형식이나 규칙이 바뀌면 세션 ID 를 얻지 못하거나 컨테이너 폴더를 찾지 못해 FAIL 로 끝난다 (fail-closed, w2d3).
  - 반영: 출력 형식이 바뀌면 러너와 tools/mock 을 같이 고친다. 장기적으로는 agent-run 이 세션 ID 와 컨테이너 폴더를 명시적으로 출력하게 하는 것을 검토 (3주차 이후, 선택)
- **사람이 의도한 호스트 실행과 자동 실행을 구분하지 못함** (`write_exec_boundary`)
  - 이유: write_exec_boundary 는 실행한 쪽의 cgroup 이 쓴 세션과 다르다는 것만 본다. 개발자가 에이전트가 빌드한 결과물을 호스트 셸에서 직접 실행하는 정상 흐름도, 호스트의 자동화(크론, CI, IDE 확장 등)가 에이전트의 파일을 실행하는 경우와 같은 BLOCK 이 된다. scenarios/n06_host_runs_output 이 이 동작을 기대값으로 고정한다 (write_exec_boundary BLOCK 1, kill/already_gone 1, 컨테이너 안 SUSPECT 0). VM 에서 러너로 다섯 번 돌려 모두 같았고, 반복 안정성을 확정한 것은 아니다.
  - 비고: 사후 차단이라 호스트의 실행 자체는 멈추지 않는다. 세션은 호스트 실행 전에 이미 끝나 있어 종료 시도는 already_gone 으로 기록된다. 완화 방향은 아직 정하지 않았다 (실행한 쪽의 맥락 확인, 검토가 끝난 산출물의 해시 허용 목록, 세션 밖 실행을 BLOCK 이 아닌 경고 수준으로 낮추기 등). 설계 메모(design-memo-w2) 8절의 "BLOCK 대응 대상" 열린 질문과 연결된다.
  - 반영: README 한계 섹션(w5). 완화 여부는 v0.2 이후에 다시 본다.
