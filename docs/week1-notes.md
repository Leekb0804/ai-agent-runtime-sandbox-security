# v0.1 1주차 메모: 알려진 한계

1주차 관측 배관(execve → ring buffer → 로더 → JSON)의 알려진 한계.
"시점"은 해결 예정 시점이다. 해결하면 체크하고, "해결" 줄에 해결 커밋의 제목을 적는다.

## 해결할 것

### 로그 무결성

- [x] **loader.c가 filename을 JSON 이스케이프하지 않음**
  - 이유: 따옴표·개행이 든 파일 이름을 exec하면 가짜 JSON 줄을 끼워 넣어 로그를 위조할 수 있다.
  - 시점: w1d3
  - 해결: "w1d3: 탐지기 디스패처와 더미 탐지기, JSON 이스케이프 추가"

### 관측 범위

- [ ] **execveat은 관측하지 않음**
  - 이유: sys_enter_execve만 붙어 있어 execveat(fexecve 포함)으로 실행하면 이벤트가 남지 않는다.
  - 시점: w4
  - 해결: (미해결)
- [ ] **세션마다 부트스트랩 EXEC(/proc/self/exe)가 먼저 기록됨**
  - 이유: mycontainer_run이 phase2 진입을 위해 스스로를 re-exec하는 것이므로, 탐지기가 이를 에이전트 행동으로 오인하지 않게 걸러야 한다.
  - 시점: w2
  - 해결: (미해결)

### fail-closed

- [ ] **로더가 꺼져도 pin된 map이 남아 있어 agent-run이 조용히 성공함**
  - 이유: map 등록은 성공하지만 프로그램이 detach돼 있어 관측 없이 세션이 실행된다.
  - 시점: w2
  - 해결: (미해결)
- [ ] **bpf_obj_get 실패 시 아무 출력 없이 진행함** (`mycontainer_run.c`)
  - 이유: 로더를 한 번도 띄우지 않아 map이 없을 때도 감시 없이 컨테이너가 실행되고, 사용자는 이를 알 수 없다.
  - 시점: w2
  - 해결: (미해결)
- [ ] **ring buffer 드롭 카운터 없음**
  - 이유: 버퍼가 가득 차면 `bpf_ringbuf_reserve` 실패로 이벤트가 버려지는데, 몇 개가 버려졌는지 남지 않아 로그 누락을 감지할 수 없다.
  - 시점: w2
  - 해결: (미해결)
- [ ] **탐지기가 연속 오류 5회를 내면 영구히 꺼지고, 알림은 stderr 한 줄뿐** (`dispatcher.c`)
  - 이유: 꺼진 탐지기를 다시 켜는 경로가 없어, 이후 세션 내내 그 탐지기의 판정이 나오지 않는다.
  - 비고: 공격자가 오류를 유발해 탐지기를 끌 수 있음(fail-open), kill switch 연결 시 fail-closed 정책과 함께 결정
  - 시점: w3
  - 해결: (미해결)
- [ ] **탐지기가 16개(MAX_DETECTORS)를 넘으면 경고만 남기고 등록하지 않음** (`dispatcher.c`)
  - 이유: 등록에 실패한 탐지기가 빠진 채로 로더가 정상 시작해, 감시가 빠졌다는 사실을 알기 어렵다.
  - 비고: 등록은 main 이전이라 실패 플래그를 세우고 main에서 시작을 거부하는 방식 검토
  - 시점: w2
  - 해결: (미해결)

## 수용한 한계

고치지 않고 감안해서 설계할 성질. 체크박스를 쓰지 않는다.

- **busybox 내장 명령은 execve가 보이지 않을 수 있음**
  - 이유: 셸 내장(applet)으로 처리되면 새 프로그램을 exec하지 않으므로 커널에서 관측할 지점이 없다.
  - 반영: README 한계 섹션(w5), 시나리오 작성 규칙(w2부터: 명령은 경로를 명시하고 이벤트가 실제로 나오는지 먼저 확인), v0.2 실제 에이전트 rootfs와 이벤트 양 비교
- **pid만으로 프로세스를 구분하면 안 됨**
  - 이유: exec는 PID를 유지하므로 같은 pid에서 서로 다른 프로그램의 이벤트가 연달아 나온다.
  - 반영: w2 설계 메모(태깅 키), README 한계 섹션
- **탐지기가 세그폴트를 내면 로더 프로세스 전체가 죽음** (`dispatcher.c`)
  - 이유: 탐지기 계층의 fail-open. C에는 예외 처리가 없어 오류 격리는 반환값으로만 가능하고, 완전한 격리에는 탐지기를 별도 프로세스로 분리해야 한다.
  - 반영: README 한계 섹션(w5), 프로세스 분리는 v0.3 이후 검토
- **탐지기 실행 순서가 보장되지 않음**
  - 이유: 탐지기는 constructor로 등록되는데, 파일 간 constructor 호출 순서는 C 표준이 정하지 않으며 링크 순서(build.sh의 detectors/*.c 확장 순서)와 툴체인에 따라 달라진다.
  - 반영: w2 설계 메모(탐지기는 서로 독립이고 실행 순서에 의존하지 않는다는 작성 규칙)
- **json_escape가 0x80 이상 바이트를 그대로 출력함** (`json_escape.c`)
  - 이유: 유효하지 않은 UTF-8 바이트열이 섞이면 일부 JSON 파서가 그 줄을 거부할 수 있다.
  - 반영: w5 로그 스키마 확정 시 파서 동작 확인, README 한계 섹션
