# 위협 모델 (2주차 확정본)

상태: **확정본(w2d2, 사용자 확인).** 이 문서의 한계는 학습용 구현의 범위를 정직하게 적은 것이다. 표기: [계획서] 계획서에 있는 내용 / [인수인계] 인수인계 문서 / [VM확인] 사용자 VM 출력으로 확인 / [추론] 판단 / [확인필요] 아직 검증하지 못함.

## 1. 이 문서의 성격

- 이 도구는 **프로덕션 보안 제품이 아니라 학습용 구현**이다. [계획서]
- 격리는 호스트 커널을 공유하는 컨테이너(namespace + cgroup + overlay rootfs)이며 gVisor나 Firecracker 수준이 아니다. 이 도구는 격리를 대신하는 것이 아니라 **격리가 놓친 행동을 에이전트 바깥에서 지켜보는 안전망 계층**이다. [추론]
- 더 강한 격리 위에서는 수집부(eBPF 프로브)를 교체해야 하며 판정부의 재사용 가능성은 설계상의 가능성일 뿐 검증되지 않았다. 향후 과제로 둔다. [추론]

## 2. 신뢰 가정

| 구분 | 대상 |
|---|---|
| 신뢰함 | 호스트 커널, 감시 로더(`myc_loader`), 호스트 쪽 판정과 로그 저장 |
| 신뢰하지 않음 | 컨테이너 안의 에이전트와 그 하위 프로세스, 에이전트가 쓴 파일의 **내용**과 이름, 프로세스 이름(`comm`) |
| 사실 | 에이전트는 사용자 네임스페이스 안 root(`uid=0`, `CapEff=000001ffffffffff`)이고 호스트 기준 uid 1000이다. 하드닝(비root, cap 축소, `no_new_privs`)은 적용하지 않았다 [VM확인] |
| 사실 | 런처(`mycontainer_run`)도 세션 cgroup 안에 있다. "세션 cgroup 안의 프로세스가 쓴 파일"과 "에이전트가 쓴 파일"이 완전히 같지는 않다 [VM확인] |

## 3. "차단"의 두 가지 의미

| 의미 | 설명 | 현재 구조에서 |
|---|---|---|
| (a) 후속 행동 중단 | 판정 후 세션 cgroup 안의 프로세스를 끊어 에이전트가 행동을 이어 가지 못하게 함(`kill_session`) | 가능. 실제 kill은 3주차, 지금은 `would_kill` 기록만 [인수인계] |
| (b) 실행 자체 저지 | 실행되기 전에 거부함 | 불가. 판정이 `exec` 이후에 나오는 사후 차단이다. 커널 안 거부는 v0.3 실험 후보 [인수인계] |

이 문서에서 "막는 것"은 **(a)** 를 뜻한다. 세션 **밖**에서 일어난 실행은 세션 kill로 멈추지 못한다. 이 구분은 README 한계 섹션에도 적는다(w5).

## 4. 대응 구분

### 4.1 막는 것 (BLOCK, 의미 (a))

| 항목 | 근거 |
|---|---|
| 세션 안에서 쓴 파일을 세션 밖에서 실행 | 계획서 §5 판정 원칙의 예시, 패턴 3. 정상 작업과 겹칠 가능성이 가장 낮다 [계획서] |

문제가 되는 이유: 파일 내용은 신뢰하지 않는 에이전트가 정한 것인데, 울타리 밖의 더 높은 권한의 프로세스가 그것을 실행하면 컨테이너 탈출 취약점 없이도 격리의 목적이 무너진다. 현재 구조에서 에이전트가 쓴 파일은 호스트의 upperdir 경로(예: `/var/lib/mycontainer/containers/<id>/upper/...`)에서 호스트 uid 1000 소유로 보이며, 호스트 프로세스가 이를 직접 실행할 수 있다 [VM확인]. 태그 판정은 `(s_dev, i_ino)`와 cgroup으로 하므로 에이전트가 파일 이름이나 프로세스 이름을 바꿔도 회피되지 않는다 [추론].

### 4.2 기록만 (SUSPECT)

| 항목 | 기록하는 이유 | 정상일 수 있는 경우 |
|---|---|---|
| 같은 세션이 쓴 파일을 같은 세션이 실행 | 에이전트가 만든 코드의 실행 | 컴파일 후 즉시 실행(빌드) |
| 최종 경로 불일치(호출 이름의 basename과 실제 실행 파일이 다름) | PATH/alias 조작, 위장 바이너리 | 심볼릭 링크로 연결된 정상 명령 [확인필요: busybox rootfs에서] |
| 쓰기 가능 디렉터리(workspace, `/tmp`)의 바이너리 실행 | 실행 시점에 받아 온 페이로드 | 컴파일 후 즉시 실행 |

- 판정 등급(SUSPECT)은 계획서에 명시되어 있지 않고 **[추론]** 이며 사용자 확인으로 확정했다.
- 기록의 목적: 사후 검토, 오탐률 측정(계획서 §4 확인 질문), 여러 신호의 상관 판단, BLOCK이 난 경위 설명.

### 4.3 범위 밖 / 한계 (위험이 없다는 뜻이 아님)

| 종류 | 항목 | 위험 | 안 하는 이유 |
|---|---|---|---|
| 스코프 아웃 | 환경변수 상태 추적 | 있음(패턴 5) | 명령 사이 상태 추적이 필요해 구현 범위가 큼 [계획서] |
| 스코프 아웃 | 특권 소켓(Docker 소켓 등) | 큼 | 탐지보다 컨테이너에 마운트하지 않는 것이 1차 방어 [계획서][추론] |
| 구조적 한계 | 순간적으로 끝나는 행동, 세션 밖 실행 자체 | 있음 | 판정이 `exec` 이후의 사후 차단이고 kill은 세션 cgroup만 끊음 [인수인계] |
| 구조적 한계 | 에이전트가 ns 안 root(전체 capability) | 있음 | 하드닝은 실험에서 바뀌는 조건을 늘리지 않으려고 v0.1에서 적용하지 않음. 탐지기가 선 뒤 별도 작업(w3 이후, 선택) [VM확인] |
| 미탐 | rename, hardlink, mmap 쓰기, 복사 후 실행 | 있음 | 태깅이 `security_file_open`의 쓰기 모드 open 시점만 대상 [VM확인] |
| 미탐 | 에이전트가 쓴 파일이 exec 대상이 아니라 인터프리터의 인자나 설정으로 읽히는 실행 (`sh <파일>`, `python x.py`, 설정 파일 안의 명령) | 있음 | `security_bprm_check` 가 exec 되는 파일의 신원만 조회하고 읽기 open 은 조회하지 않음. 같은 파일을 `sudo sh <파일>` 로 실행하면 `TAG_HIT` 이 없고 직접 실행하면 BLOCK 이 남 [VM확인, sh 한 번 기준] |
| 관측 한계 | busybox 내장 명령 | 명령에 따라 다름 | `execve`가 없어 이벤트가 남지 않음. `/bin/ls`처럼 경로를 명시해야 이벤트가 남음 [인수인계] |
| 관측 한계 | TLS 내용 | 암호화된 반출은 내용을 못 봄 | 커널에서는 암호화된 바이트만 보임. 평문 관측에는 사용자 공간 uprobe나 프록시 필요 [추론] |

## 5. 계획서 5개 패턴과의 대응

| 패턴 | 이 도구의 대응 | 성격 |
|---|---|---|
| 1 검사기가 셸 파싱을 못 흉내냄 | 경로 비교 탐지기가 최종 `execve` 결과만 봄 | **간접**: 우회 기법이 아니라 우회 성공 후의 결과를 포착 |
| 2 안전장치가 LLM 출력 필드 | 위와 같음 | 간접 |
| 3 신뢰 경계가 프로세스 밖으로 샘 | 쓰기→실행 탐지기(`TAG_HIT`) | **직접**(BLOCK) |
| 4 정적 페이로드 없음 | v0.3 DNS 조회→셸 실행 상관 | v0.3 |
| 5 명령 간 상태 이용 | 경로 불일치가 일부를 결과로 포착, 환경변수 추적은 범위 밖 | 부분 |

## 6. 이 문서가 아직 확인하지 못한 것

- 호스트의 **비root** 프로세스가 에이전트 파일을 실행하는 경우, 실행 중인 세션의 파일을 호스트가 실행하는 경우. 이번 검증은 root(`sudo`)가 세션 종료 후의 파일을 실행한 한 번이다.
- 모든 exec 경로가 `security_bprm_check`를 지나는지(`static` 함수라 인라인될 수 있음).
- `dev=40` 같은 overlay 장치 번호의 컨테이너 간 재사용.
- 경로 비교 탐지기의 오탐: busybox 심볼릭 링크, 빌드 후 즉시 실행의 빈도.
- BLOCK 의 대응 대상(쓴 세션 종료가 적절한지, 오탐 시 비용)은 열린 설계 질문이다. 설계 메모 8절 참고. 3주차 오탐 측정 뒤에 정한다.

## 7. 검증과의 연결

- 기존 시나리오 `s00_benign`, `s99_dummy_block` [인수인계]. 이후 추가 후보(이름은 제안): `s01_write_exec_cross`(세션에서 쓴 파일을 세션 밖에서 실행, BLOCK), `s02_write_exec_same_session`(빌드 후 실행, BLOCK 아님), 경로 불일치(SUSPECT), 범위 밖 항목이 기록되지 않음을 보이는 음성 시나리오.
- 세션 밖 실행 재현에는 `host.sh` 같은 호스트 쪽 스텝 지원이 필요하다. 호스트 쪽 스크립트가 세션 cgroup 밖에서 실행되는지 먼저 확인한다(결정 7번).
